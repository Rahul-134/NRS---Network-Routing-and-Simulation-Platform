# API reference

The backend is stateless. Each simulation request carries the whole topology, and the response contains every step. The frontend animates the steps locally.

Interactive documentation is generated by FastAPI at http://127.0.0.1:8000/docs while the backend is running.

## Data model

```json
{
  "topology": {
    "nodes": [{ "id": "A", "label": "A", "x": 60, "y": 190 }],
    "links": [{ "id": "A-B", "source": "A", "target": "B", "cost": 4, "enabled": true }]
  },
  "source": "A",
  "destination": "F"
}
```

Links are undirected. `x` and `y` are only used by the frontend for layout.

### Validation rules

| Rule | Error |
| --- | --- |
| Router ids and labels are unique | Duplicate router id / label |
| Link ids are unique | Duplicate link id |
| Links join two existing routers | Link refers to a router that does not exist |
| No link from a router to itself | Link connects a router to itself |
| At most one link between two routers | Duplicate link between the two routers |
| Cost is a positive integer | Link must have a positive cost |
| Source and destination exist | Source / destination router does not exist |

Invalid topologies return HTTP 422 with `detail` set to a list of messages. A request with the wrong shape (missing fields, wrong types) also returns 422 in FastAPI's standard format.

## Endpoints

### `GET /api/health`

Returns `{"status": "ok"}`.

### `POST /api/simulations/validate`

Body: the data model above. Returns `{"valid": true, "errors": [], "connected": true}`. `connected` is `null` when the topology is invalid.

### `POST /api/simulations/dijkstra`
### `POST /api/simulations/distance-vector`
### `POST /api/simulations/link-state`

Body: the data model above. Every response has these fields:

| Field | Meaning |
| --- | --- |
| `algorithm` | `dijkstra`, `distance_vector` or `link_state` |
| `source`, `destination` | The requested routers |
| `steps` | List of simulation steps (see below) |
| `final_path` | Router ids from source to destination, or `null` when there is no route |
| `total_cost` | Cost of the final path, or `null` |
| `hop_count` | Number of links on the final path, or `null` |
| `iterations` | Nodes processed (Dijkstra), update rounds (Distance Vector), flooding rounds (Link State) |

Every step has `step` (its index), `type`, `active_links` (link ids highlighted at that step) and `explanation` (a sentence for the UI).

#### Dijkstra steps

`type` is `init`, `select` or `complete`.

| Field | Meaning |
| --- | --- |
| `current` | Router selected in this step, or `null` |
| `visited` | Routers whose distance is final |
| `candidates` | Unvisited routers with a known distance |
| `distances` | Router id to distance, `null` for unreachable |
| `predecessors` | Router id to the router before it on its best path |
| `changed` | Routers whose distance improved in this step |

#### Distance Vector steps

`type` is `init`, `round` or `complete`. The response also has `converged` (false only if the round limit was hit).

| Field | Meaning |
| --- | --- |
| `round` | Round number, 0 for `init` |
| `tables` | `{router: {destination: {cost, next_hop}}}`, `cost` is `null` when unknown |
| `changes` | List of `{router, destination, old_cost, new_cost, old_next_hop, next_hop}` |
| `changed_routers` | Routers whose table changed in this round |

#### Link State steps

`type` is `init`, `flood`, `spf` or `complete`. The response also has `lsas`: for each router, the list of `{neighbor, cost}` it advertises.

| Field | Meaning |
| --- | --- |
| `round` | Flooding round |
| `lsdb` | For each router, the origins whose LSA it holds |
| `received` | List of `{router, origin, from}` for LSAs delivered in this round |
| `changed_routers` | Routers that received something in this round |
| `tree_links` | Links of the source's shortest-path tree (`spf` and `complete` steps) |
| `tables` | Routing tables of every router (`spf` and `complete` steps only) |

### `POST /api/simulations/compare`

Body: the data model above. Runs all three algorithms and returns:

```json
{
  "source": "A",
  "destination": "F",
  "results": [
    {
      "algorithm": "dijkstra",
      "name": "Dijkstra",
      "final_path": ["A", "C", "B", "D", "E", "F"],
      "total_cost": 13,
      "hop_count": 5,
      "iterations": 6,
      "iteration_unit": "nodes processed",
      "steps": 8,
      "converged": true
    }
  ],
  "costs_agree": true,
  "paths_agree": true,
  "best": ["link-state"],
  "tie": false
}
```

`best` lists the most efficient algorithm or algorithms: the lowest total cost first, then the fewest simulation steps. It is empty when no algorithm found a route or when all three tie, and `tie` is true when all three have the same cost and the same number of steps. Iterations use a different unit for each algorithm, so they are reported but not ranked.

### `POST /api/topologies/random`

Body (all fields optional):

| Field | Default | Range |
| --- | --- | --- |
| `nodes` | 6 | 2 to 50 |
| `extra_link_chance` | 0.3 | 0 to 1 |
| `max_cost` | 10 | 1 to 99 |
| `seed` | none | any integer, makes the result repeatable |

Returns a topology. Routers are placed on a jittered grid whose spacing shrinks from 190 to 150 pixels as the network grows from 12 to 30 routers, so large networks stay compact. The generator builds a minimum spanning tree over them, so the network is always connected, then adds extra links between nearby routers with the given chance. A link is skipped if it would cross another link or pass close to a router it does not connect, so the drawing stays readable even at 50 routers. Costs are random integers from 1 to `max_cost`.
